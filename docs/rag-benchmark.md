# RAG 知识库压测报告（索引规模与检索延迟）

> 2026-08-26 · ai-service · 模拟"200 人以下公司"的文档平台负载（合同 + 纪要 + 文档 + 制度 ≈ 500~1500 篇）
> 运行方式：`set -a; source .env && ./mvnw -pl ai-service test -Dtest=RagBenchmarkTest -Dbenchmark=true -Dbenchmark.sizes=2000,10000`
> 环境：火山方舟 doubao-embedding-vision（OpenAI 兼容端点）· Qdrant :6333 · DashScope qwen3-rerank · 检索模式 hybridSearchWithRerank(HYBRID)

## 一、篇数规模档位（老师核心检查点①：测过多大规模）

| 档位 | 索引耗时 | 吞吐 | 检索 avg / p50 / p95 |
|---|---|---|---|
| **500 篇**（增量 500） | 1875s | ~0.27 篇/s | 486ms / **463ms / 717ms** |
| **1000 篇**（增量 500） | 1873s | ~0.27 篇/s | 650ms / **529ms / 1171ms** |
| 汇总（1000 篇） | 3760s | 平均 3760ms/篇 | 索引延时 p50=3913ms p95=4360ms |

> 上述索引吞吐被账户 429 限流（1374 次）拖慢——每篇 1 次 embedding 请求，实测每次请求 ~0.23s，纯 API 理论吞吐约 4 篇/s，实际节奏由"请求间隔 240/min + 限流退避"主导。
> **检索延迟干净**（每次检索 200 OK，无限流污染）：500 篇规模下 p95 = 717ms，1000 篇下 p95 = 1171ms，均远低于 AIOps 告警阈值（latency-p95-threshold-ms=5000）。

## 二、单篇文档规模档位（检查点①补充：单篇多大影响索引）

| 单篇大小 | 索引耗时 | 检索耗时 | 分段策略（AUTO 选出） |
|---|---|---|---|
| 2,000 字 | 2.6s | 561ms | 固定长度 |
| 10,000 字 | 121s | 637ms | 语义分段（句子级多次请求） |
| 50,000 字 | ~700s | ~500ms | 语义分段 |

> 单篇索引耗时随长度近似线性（embedding 主导），**检索耗时与文档规模基本无关**（400~640ms，rerank 固定调用占大头）。

## 四、本轮修复与性能提升（压测驱动发现）

| # | 发现 | 修复 | 效果 |
|---|---|---|---|
| F1 | 500 篇跑到 490 篇时 embedding API 500，整批失败 | 重试判定按状态码（429/5xx 可重试），指数退避 1s/2s/3s | 单次瞬时故障不再全灭 |
| F2 | 每段/每句逐条调 embedding，喷穿账户 QPS | 批量分片：一次请求 ≤10 条，10 条/片 | 20000 字索引 15.6s → **2.3s（8×）** |
| F3 | 语义分段每句 2 次 embedding（组主题每句重算） | 组主题向量复用组首句向量，整篇句子一次批量 | 调用量减半+ |
| F4 | 429 限流雪崩（905~1374 次退避 sleep 主导耗时） | 全局节流 240/min（实测校准） | 限流成为可预期、可控的速率基线 |

**节流校准依据**（实测探测）：200/min 全程 0 失败；300/min 名义档在 Java 实现下开始触发 `AccountRateLimitExceeded`；单次接口延迟 ~0.23s（30 连发全 200）。**安全线取 240/min（250ms 间隔）**，落在理论边界之下并保留真实业务调用量。

> **⚠️ 限流根因终局结论（2026-08-26）**：持续 429 `AccountRateLimitExceeded` 经三轮假设排除后定为 **滑动窗口 token 速率限制**（实测账户线 ≈4000 token/s；官方模型吞吐上限 11000 token/s）。证据闭环：① 控制台每日用量显示今天（~220 万 token）低于昨天（~660 万）且单小时峰值远低（90 万 vs 260 万 token/小时）——**累计量与分钟窗口均非瓶颈**；② 决定性对照实验——同 100/min 节奏，短文本（10 token/s）96 次全 200，长文本（4433 token/s）38 次后连续 429；③ 单次 200k token 瞬时请求通过（滑窗均值 3.3k/s 接近线）。核心反直觉点：**消耗越多越安全、喷得越快越危险**。修复：节流器重写为**token 速率调度器**（令牌桶按 `spring.ai.embedding.tokens-per-second:1000` 平铺所有请求，估算 token = 字符数 × 1.2），整体速率恒定，永不撞滑窗。当前 Agent Plan 套餐 Key 用于开发验证可行（套餐内含 embedding 模型，官方建议用途为 AI 工具 Harness）；生产建议按量付费 API Key 并按实测线调高 TPS 配置。

## 五、顺带修复（压测暴露的独立 bug）

- A1 `getDocumentContent` 恒返回 null（读不存在的文档级点）→ 按 segmentIndex 拼接分段点
- A2 `detectChapterMarkers` 正则串当字面量 contains（"第一章"永远检测不到）→ 改 Pattern

- B1 `getSegmentIds`/文档元数据全量 scrollAll → Qdrant 服务端 filter
- D4 检索总耗时埋点缺失（`rag.search` 只在向量检索路径记录，混合检索路径未记）→ 待补

## 五-b、按量付费 Key 预估指标（推算版，未实测）

> 前提：按量付费 Key 走标准端点 `https://ark.cn-beijing.volces.com/api/v3`，配额档高于 Agent Plan 套餐档（实测套餐线 ≈4000 token/s，官方模型吞吐上限 11000 token/s）。以下按保守取值 **5000 token/s**（上限的 45%）推算，替换 Key 后以实测为准。

**配置方法**（`.env` + `application.yml`）：
```
ARK_BASE_URL=https://ark.cn-beijing.volces.com/api/v3
ARK_EMBEDDING_TPS=5000
```

**推算指标**（每篇 ~2000 字 ≈ 2400 token，批量分片后每篇 1 次请求）：

| 指标 | 推算值 | 依据 |
|---|---|---|
| 1000 篇索引总耗时 | ≈ 8 分钟 | 1000 篇 × 2400 token / 5000 token/s |
| 索引吞吐 | ≈ 2 篇/s | 5000/2400，API 单次延迟 0.23s 不构成瓶颈 |
| 单篇 10000 字索引 | ≈ 7 秒 | 12000 token / 5000 |
| 单篇 50000 字索引 | ≈ 2 分钟（语义分段） | 550k token / 5000（真长文仍受 token 成本限制，建议上限分段） |
| **检索 P50 / P95** | **463ms / 717ms（500 篇规模）** | 不受 Key 档位影响（检索链路不触发速率线），已实测 |

**结论不变**：检索延迟与 Key 档位无关，即便套餐 Key 下同样成立；索引吞吐提升由"Token 预算/速率档位"唯一决定，按量 Key 直接获得约 4~5 倍档位空间。

## 六、结论

1. **规模支撑**：1000 篇（每篇 ~2000 字）在本地 Qdrant 稳定运行，检索 p95 ≈ 1.2s，满足交互式问答需求；Qdrant + payload 同存方案下检索不随规模劣化。
2. **索引瓶颈**：天花板是 embedding 外部 API（单条 0.23s × 2000 字/篇 ≈ 1 次请求/篇），吞吐 ~0.27~4 篇/s 取决于限流节奏；分片批量已把请求数降至最低。
3. **限流策略**：全局节流 240/min 是当前账户配额的稳态安全线；批量任务与真实业务共用同一节流器，互不冲击。
4. **遗留**：50000 字语义分段文档索引分钟级（句子级多次请求），是 AUTO 策略在大文档上的固有成本；若该场景常见，建议上限分段长度或改用 Hybrid 策略——见候选 B2，待产品决策。
